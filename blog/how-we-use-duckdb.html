A Durable Local Task Engine for Dynamically Expanding Workloads

Design notes from the Sylos migration engine · June 2026

Note on authorship. The prose on this page was produced with AI assistance for raw text generation, then heavily reviewed, edited, and guided by the author for accuracy and quality.

Sylos is a breadth-first filesystem migration tool. This note is about the task engine behind it. The same pattern applies anywhere running a task can create more tasks: you need a durable local queue that can grow without blowing up memory or treating the database as the live scheduler on every pull.

Workers do not recurse in-process. Each task handles one item, persists any children, and stops. That child work is picked up in a later round (in Sylos, the next BFS depth level). Scheduling, leasing, and retries live in an in-memory queue; DuckDB is a durable log you refill from and append to, not the frontier itself.

Below: the pull-lease-process-append loop, the DuckDB patterns that made this practical at scale (Appender bulk writes, append-only status events with per-round materialization, and keyset batch pulls), dual-tree coordination, evaluation, and a short rebuttal of approaches that look simpler until the constraints bite.

1. Problem

A task runs, discovers child tasks, and schedules them. At scale this is not a fixed queue size. Generation can outpace consumption for long stretches, especially when one listing expands into hundreds of pending items. If pending work lives only in process memory, the backlog grows until the process fails.

The engine must therefore write results and read the next batch of pending work from the same store, survive restarts, and avoid duplicate traversal. Pure in-memory scheduling is fast but not resumable. Per-node synchronous database round-trips do not reach millions of items. The design target is a local, durable task queue with dynamically expanding work, not a distributed stream processor.

2. Engine loop

Each worker handles one node per task: list immediate children, apply filters, persist results, stop. Children become new tasks for a later round (the next BFS depth level), not on the worker's call stack. Depth is carried in the queue, not in recursion. That matters for skewed trees (one branch with millions of descendants, a sibling with none): a worker must not recurse in-process and pin work that other workers could take.

The runtime loop:

  1. Pull a batch of pending rows from DuckDB (WHERE id >= last_id LIMIT n).
  2. Lease them into an in-memory buffer for workers.
  3. Process each item (list, filter, discover children).
  4. Append new node rows, status events, and child work through a write buffer into the Appender; flush to disk.
  5. Advance last_id and repeat. On crash, restore round cursors and pull from the last known ID.

                 |   DuckDB Log   |
                 | Nodes + Events |

                          ^
                          |

2.1 DuckDB Appender

Hot-path writes go through DuckDB's Appender API, not row-by-row INSERT or UPDATE statements. Workers push node metadata and status events into an in-memory buffer; the buffer bulk-loads into the Appender and is flushed. Columnar append matches the write pattern: many new rows, few random updates.

The Appender maintains its own internal buffering. An explicit flush after draining the engine buffer defines when data is on disk for resume. That redundancy is intentional: persistence boundaries are predictable during development and after interrupts.

2.2 Append-only status events

Node metadata (src_nodes, dst_nodes) is written once. State changes are new rows in src_status_events / dst_status_events: pending on discovery, traversed or failed on completion. No UPDATE or DELETE on the hot path. 

-- Avoid on hot path
UPDATE nodes SET status = 'complete' WHERE id = 123

-- Write pattern
INSERT INTO status_events (node_id, status, ...) VALUES (...)

The event log is the write-ahead source of truth during a round. Review and status search do not scan it for "latest per node" on every query; that cost is compacted into a per-round materialized table (§2.3).

2.3 Per-round status materialization

At the end of every BFS round, after the Appender flush, the engine rebuilds a one-row-per-item table (src_current / dst_current) holding just the latest status for nodes at that depth. Mid-round frontier pulls still window-aggregate over status_events for the ids in the keyset window, because the material table is intentionally stale until the round seals. After seal, review, status counts, and arbitrary SQL predicates (status = pending, and so on) read the compact table instead of replaying the full append log.

The pattern is directly analogous to LSM-tree compaction: status_events is the write-ahead / append log, and the per-round seal step merges it into a fast, queryable materialized view. The compaction trigger is domain-specific (BFS round boundary) rather than time- or size-based as in a general-purpose LSM engine.

We A/B tested with versus without the material table and saw roughly 8× faster query times on large tables with it, so it was worth the complexity.

2.4 Keyset batch pulls

Pending work is fetched in batches. The original motivation for keyset pagination was not OFFSET scaling. Under fast, high-throughput runs we hit a DuckDB read-after-write inconsistency on the same connection: a flush would report success, but a subsequent query would not always see the newly written rows yet. The bug did not reproduce at manual / slow testing speed, which made it hard to track down. So it took hours of debugging to discover what the true issue was given this tricky runtime behavior. Re-querying "what is still pending?" after each flush was therefore unsafe as a scheduling primitive.

Switching to a cursor-based approach (track last pulled ID + 1, rather than asking the database what remains pending) sidestepped the problem: the engine stopped depending on DuckDB's read-your-writes guarantee instead of trying to work around its timing. The pull becomes: 

WHERE id >= :last_id
LIMIT :batch_size

A secondary benefit is that keyset pagination avoids OFFSET's O(n) scan cost at large offsets (offset 50,000,000 implies scanning past 50M rows on every page). Each pull is an O(1) seek to last_id plus a bounded read of batch_size rows, so pull cost stays flat as the table grows. That OFFSET win is real, but it was not the original driver.

Appender batching still means completed work can look pending in DuckDB until the next flush. That does not corrupt pagination because rounds are sealed at a fixed depth: work at round N only inserts children at depth N+1, so the src_nodes rows at depth N are stable for the round. What grows mid-round is status_events. Pulls use id >= cursor with a pending filter over the keyset window; the cursor advances to the last enqueued id. Once leased into memory, an id is not pulled again. Round completion is driven by in-memory state (empty lease buffer, nothing in progress, last pull partial), not live DB pending counts. Before advancing, the engine flushes then rebuilds *_current for the finished depth (§2.3).

Consistency model.

Layer Role during round N
Lease buffer + in-progress set Truth for what is live this round
DuckDB nodes + status events Truth for what exists; frontier refill and resume
Appender flush Async write path; forced before round advance
src_current / dst_current Sealed latest status for finished depths; review / search after round advance

Deliberate tradeoff: the DB can show more pending rows than memory during a round. Cursor discipline and in-memory completion prevent double work.

2.5 Task retries and leasing

What about task retries? Retries are handled entirely inside the lease queue. The database is not re-queried to discover that a task needs another attempt. A row is pulled from DuckDB into the queue once; from there the queue owns its lifecycle until the task succeeds or is exhausted.

Workers do not take tasks directly from the database. They ask the queue for work. The queue mutex-locks a task for one attempt at a time. On each attempt, whether it succeeds or fails, the worker pushes results into the DB buffer so progress is persisted and resumable if the process crashes mid-retry. If the attempt succeeds, or fails after the configured maximum (for example three attempts), the queue records the final outcome and removes the task. If the attempt fails but retries remain, the queue records the attempt, unlocks the task, and another worker can pick it up.

The queue is the authority on leasing. Workers report attempt completion; they do not decide unilaterally when a task leaves the active set. That keeps retry state out of the hot pull path and consistent with the memory-first scheduling model in §2.4.

3. Dual-tree coordination

Migration compares two trees. Destination work depends on what the source has already discovered at the corresponding level. The source queue may run as far ahead as workers allow. The destination may run at full speed but only through source round minus one: if the source is on round 5, the destination waits on round 4 until the source begins round 6.

Finer-grained gating per subtree is possible. Round-level gating was chosen for simpler invariants and resume behavior at the cost of slightly conservative destination pacing.

Note. The destination queue and coordinator exist for two-tree comparison. Single-graph workloads drop that layer:

Pull → Lease → Process → Append → repeat.

4. Evaluation

Benchmarks use Spectra for reproducible trees without real I/O; see the Spectra design note for the harness. On live storage, throughput is near parity with Rclone because both systems become I/O bound. Under Spectra ephemeral mode, engine overhead (persistence, events, coordination) appears as roughly 10 to 30% additional cost versus a tool that does not carry the same guarantees.

Environment Observation
Real storage Near parity with Rclone; disk and API limits dominate.
Spectra ephemeral (no I/O) ~10 to 30% slower than Rclone; persistence and coordination overhead visible.

Throughput numbers are only meaningful alongside what guarantees they cost. Sylos pays for a persistent event log, resumable queue state, and reconstructable review metadata. Rclone's traversal path does not carry equivalent machinery.

5. Couldn't you just…?

The shape above is not the first thing we tried. Most "obvious" database approaches fail against a tight constraint set: tables that must scale to at least ~20M rows, a local embedded store (no separate DB server), very fast writes on the hot paths, like traversal mode or copy modes, and acceptably fast reads afterward. Writes and reads are slightly separated workloads, but the review phase still does large subtree updates and those have to finish in an acceptable amount of time. Memory complexity, time complexity, and developer complexity all matter: something that works at a few hundred thousand rows, or only if you keep the frontier in RAM, does not count.

Why not just use a k/v store with secondary indexes?

An earlier version of this engine ran on BoltDB and tried to buy read speed with hand-built secondary indexes: membership buckets per status per level, a reverse status-lookup bucket, and bidirectional src-to-dst / dst-to-src join buckets so correlating the two trees did not require an expensive read-time join. Each status transition touched several buckets atomically (update the node, move membership, refresh the lookup).

Reads of known shapes were fast. Scale and ad-hoc review search were not. Even before the hundred-gigabyte stress cases, the central nodes bucket itself bogged down. As a B+tree grows, write amplification climbs: each insert or update touches more pages for splits and rebalancing, and Bolt's copy-on-write path rewrites those pages on the way down. Depth grows only logarithmically, but the constant factor per operation (pages read, copied, and rewritten) rises steadily until it stops being hideable. That degradation is roughly linear rather than a sudden cliff; past roughly 200K entries it crossed into multi-second inserts and updates on that bucket, so write throughput collapsed long before Appender-style LSM bulk loads would. Partitioning the nodes table to keep each B+tree small was the natural next try; it bought a temporary reprieve and roughly 10× more developer complexity, then the same wall per partition.

A larger stress test with ~40M source nodes and ~20M destination nodes then grew the file to roughly 100GB: empty membership values meant Bolt's per-entry overhead dominated the payload, and multi-bucket writes stacked more amplification on top of COW. With no background compaction, that bloat stayed until a manual rewrite. Review-phase search was worse still: anything beyond the pre-built index shapes meant more reverse indexes or near-impossible hand-rolled scans. That path was scrapped for a simpler SQL approach in DuckDB. The lesson that carried forward was not "don't build indexes," but that indexes must earn their storage and maintenance cost, and an engine without compaction holds you to the storage cost forever. The Appender path plus per-round *_current compaction (§2.3) is the same space-for-speed trade, periodically reclaimed, with ordinary SQL predicates for review search instead of another layer of buckets.

Mutable status rows?

Separately, treating the database as a mutable task table (insert, select pending, update status) also failed at volume. Prototyping hit throughput walls around hundreds of thousands of rows on Bolt, SQLite, and DuckDB when updates dominated. The same prototype also hit the read-after-write inconsistency in §2.4 when it treated DuckDB as the live scheduler on every pull. Append-only events, keyset cursors, and memory-first round completion replaced that model.

Keep the frontier in memory?

This is the obvious first choice, and it looks like it works until you implement it. A prototype held the current source level and its children in RAM until the destination consumed them. If the source ran ahead, the cache grew faster than the destination could drain it. Gating the source per level capped growth but still required roughly two frontier levels in memory at once.

The deeper problem is that RAM does not buy you out of durability. Resumability still requires periodic WAL-style flushes of updates into the database, so the write cost is only deferred, not removed. Producers (workers finishing tasks) can outrun the consumer (flushing the DB buffer to disk), which is a leaky-bucket problem: you keep going through a DB stall, then pay the same write throughput later with a larger backlog and less safety if the process dies mid-buffer. Evicting into the DB buffer only shifted growth to another in-memory structure until flush. You can tune that for speed if you accept unbounded (or carefully gated) RAM and weaker resume guarantees; under the 20M-row embedded constraint, the current design does not. DuckDB is the durable log; the lease queue is only the live scheduler for the active round.
