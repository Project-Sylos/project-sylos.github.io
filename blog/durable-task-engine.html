A Durable Local Task Engine for Dynamically Expanding Workloads

Design notes from the Sylos migration engine · October 2026

Note on authorship. The prose on this page was produced with AI assistance for raw text generation, then heavily reviewed, edited, and guided by the author for accuracy and quality.

Sylos is a breadth-first filesystem migration tool. This note is about the task engine behind it. The same pattern applies anywhere running a task can create more tasks: you need a durable local queue that can grow without blowing up memory or treating the database as the live scheduler on every pull.

Workers do not recurse in-process. Each task handles one item, persists any children, and stops. That child work is picked up in a later round (in Sylos, the next BFS depth level). Scheduling, leasing, and retries live in an in-memory queue. The per-migration Badger ops store ({id}.ops/) is the operational source of truth you refill from and seal into, not the frontier itself for the active round.

Below: the pull-lease-process-seal loop, the Badger patterns that make it practical at scale (trusted seal batches, catalog vs status overlay vs frontier keys, and planned review search), dual-tree coordination, and a short rebuttal of approaches that look simpler until the constraints bite.

1. Problem

A task runs, discovers child tasks, and schedules them. At scale this is not a fixed queue size. Generation can outpace consumption for long stretches, especially when one listing expands into hundreds of pending items. If pending work lives only in process memory, the backlog grows until the process fails.

The engine must therefore write results and read the next batch of pending work from the same store, survive restarts, and avoid duplicate traversal. Pure in-memory scheduling is fast but not resumable. Per-node synchronous database round-trips do not reach millions of items. The design target is a local, durable task queue with dynamically expanding work, not a distributed stream processor.

2. Engine loop

Each worker handles one node per task: list immediate children, persist results, stop. Children become new tasks for a later round (the next BFS depth level), not on the worker's call stack. Depth is carried in the queue, not in recursion. That matters for skewed trees (one branch with millions of descendants, a sibling with none): a worker must not recurse in-process and pin work that other workers could take.

Filters are a separate concern. Exclusion rulesets run over the already-discovered inventory during review; they do not steer BFS while discovery is listing children.

The runtime loop:

  1. Pull a bounded batch of pending work from Badger (pend:* keyset by depth and type, with batched node/status prefetch; §2.4).
  2. Lease them into an in-memory queue for workers.
  3. Process each item (list, discover children, copy, or delete).
  4. Buffer catalog inserts, status overlays, frontier deltas, and related side effects into the seal buffer; flush that buffer to Badger on a row/time threshold, under backpressure, or before round advance (§2.1).
  5. Advance the pull cursor and repeat. On soft suspend or crash recovery, restore round cursors and pull again from Badger.

2.1 Seal buffer and trusted batches

Workers never open a Badger write transaction per tiny completion on the hot path. Completions, discoveries, status updates, frontier deltas, kids packs, and related rows land in an in-memory seal buffer shared by the phase. The buffer drains on a row threshold, a short timer, backpressure (hard cap), or an explicit flush before round advance. That drain is what makes "millions of tasks" compatible with one embedded store: the hot path is enqueue-to-memory; the disk path is bulk.

Flushes call a trusted batch writer. The flush path does not probe Badger for whether a pending key already exists or what the prior status row was. Callers supply that context from the task (InsertOnly, PrevStatus, PendWasSet). Probes on every sealed row would kill throughput; trust plus batching keeps discovery and copy CPU on FS I/O and queue leasing.

Hard caps matter. If seal cannot keep up, producers block. That backpressure is intentional: you do not silently grow an unbounded in-memory backlog while pretending the durable log is still the safety net.

2.2 Schema mental model

You do not need every key prefix memorized. These families matter day to day:

Family Plain English
node:… Catalog row for one SRC or DST item (path, name, size, …).
st:… Phase-split status overlay (traversal / copy / delete) for that item.
pend:… Still-need-to-work frontier keys, ordered by depth and type.
child: / kids: Tree edges and packed child snapshots for a parent.
idx:… Secondary indexes for path, name, size, mtime, segments, trigrams.
map:… SRC↔DST identity pairing after copy.

Catalog and status are separate on purpose: discovery can stamp many nodes; later phases rewrite status (and sometimes frontier) without rewriting the whole catalog row every time. Indexes for later search are written when catalog nodes are inserted, not in a giant end-of-phase rebuild.

There is no per-migration DuckDB. The logical path {id}.db is a historical marker name only. Queues, review UI, resume, and stats all go through Badger.

2.3 Status overlay and frontier

Node metadata is written as catalog rows. State changes update the status overlay and adjust frontier keys. Mid-round, workers seal status transitions and enqueue the next depth's pend:* entries through the same buffer. There is no separate "materialize current status" step at round boundaries: the overlay and frontier are the current view.

That is the physical-model change from an earlier DuckDB design, which appended status events and rebuilt a slim one-row-per-item table each round. The control loop stayed the same; Badger's key layout made a live overlay and sorted frontier the simpler fit than SQL event compaction.

Consistency model.

Layer Role during round N
Lease buffer + in-progress set Truth for what is live this round
Badger node / st / pend Truth for what exists; durable frontier and resume
Seal buffer → trusted flush Async write path; forced before round advance / soft suspend
idx:* + review planner Candidate sets for path review / search (read path)

Deliberate tradeoff: Badger can still show more pending frontier than memory during a round until the next flush. Cursor discipline and in-memory completion prevent double work.

2.4 Keyset batch pulls

Pending work is fetched in batches sized for the lease queue (on the order of thousands of tasks per refill, not "everything still pending"). Pulls seek the frontier by depth, type, and cursor, not OFFSET over a giant pending list, and prefetch node and status fields in the same batched APIs. Destination rounds add expected SRC children for comparison, with a separate hydration cap so dual-tree expected maps do not blow RSS.

The queue does not need live global "count still pending in the DB" to stay correct. Round completion is driven by in-memory state (empty lease buffer, nothing in progress, last pull partial, at least one pull attempted), not a follow-up aggregate over the store. The cursor advances to the last enqueued id. Once leased into memory, an id is not pulled again for that attempt lifecycle.

Soft suspend clears the in-memory lease buffer and in-flight set, flushes seal, and keeps Badger. Resume restores round numbers and keyset cursors, then pulls again. Leased task IDs are not persisted as a separate lease log; the frontier in Badger is what you come back to.

Rule of thumb on the hot path: prefetch in batched pull/list APIs, compare in memory, and only append to the seal buffer. Do not fetch a node by id inside a per-item completion loop.

2.5 Task retries and leasing

What about task retries? Retries are handled entirely inside the lease queue. The store is not re-queried to discover that a task needs another attempt. A row is pulled from Badger into the queue once; from there the queue owns its lifecycle until the task succeeds or is exhausted.

Workers do not take tasks directly from the database. They ask the queue for work. The queue mutex-locks a task for one attempt at a time. On each attempt, whether it succeeds or fails, the worker pushes results into the seal buffer so progress is persisted and resumable if the process crashes mid-retry. If the attempt succeeds, or fails after the configured maximum, the queue records the final outcome and removes the task. If the attempt fails but retries remain, the queue records the attempt, unlocks the task, and another worker can pick it up.

The queue is the authority on leasing. Workers report attempt completion; they do not decide unilaterally when a task leaves the active set. That keeps retry state out of the hot pull path and consistent with the memory-first scheduling model in §2.4.

3. Dual-tree coordination

Migration compares two trees. Destination work depends on what the source has already discovered at the corresponding levels. The source queue may run as far ahead as workers allow; frontier and catalog seal into Badger as it goes. The destination may start round N only after the source has completed rounds N and N+1 (or source traversal is finished): a two-round lead so parent and child context exist before DST comparison tasks are built.

Finer-grained gating per subtree is possible. Round-level gating was chosen for simpler invariants and resume behavior at the cost of slightly conservative destination pacing.

Note. The destination queue and coordinator exist for two-tree comparison. Single-graph workloads drop that layer:

Pull → Lease → Process → Seal → repeat.

4. Review: batch on write, plan on read

Between phases, the UI browses and searches the discovered tree. Those screens are read-mostly against Badger: folder children, merged SRC/DST review rows, status overlays, and keyset pagination. Mutations during review (exclude, mark retry, delete skip) still go through sealed status and frontier updates. They are not a separate staging table.

Arbitrary search is planned, not "scan every node every time":

  1. Look at the query (path segments, name contains, size/mtime bounds, status filters, …).
  2. Pick the cheapest candidate source among secondary indexes (path, segments, trigrams, size/mtime) or a capped status walk.
  3. Hydrate those ids into node + status records.
  4. Apply remaining predicates in Go and page the results.

Path search is ordered folder parts, not free-form "substring anywhere in the path." Name substring uses trigrams. Ruleset path operators (contains / glob / regex) are a third system used for exclusion predicates; they are intentionally separate from the review search bar.

Closing rule of thumb: batch on the write path, plan on the read path, and treat {id}.ops/ as the source of truth.

5. Evaluation

Benchmarks use Spectra for reproducible trees without real I/O; see the Spectra design note for the harness. On live storage, throughput is dominated by disk and API limits for any engine that streams bytes. Under Spectra ephemeral mode, persistence, events, and dual-tree coordination show up as measurable engine overhead relative to a tool that does not carry the same guarantees.

6. Couldn't you just…?

The shape above is not the first thing we tried. Most "obvious" database approaches fail against a tight constraint set: tables that must scale to at least ~20M rows, a local embedded store (no separate DB server), very fast writes on the hot paths (traversal and copy), and acceptably fast reads afterward. Writes and reads are slightly separated workloads, but the review phase still does large subtree updates and those have to finish in an acceptable amount of time. Memory complexity, time complexity, and developer complexity all matter: something that works at a few hundred thousand rows, or only if you keep the frontier in RAM, does not count.

Why not Postgres (or any server SQL database)?

Postgres is an excellent general-purpose database. It is the wrong packaging for this product. Sylos is meant to run as a self-hosted appliance beside the filesystems it migrates: one process, one migration directory, resume after a reboot without standing up a database server, connection pool, backups, and upgrade story next to the engine. A remote SQL server also turns every seal flush and frontier refill into network-bound work on a path that already has to keep up with listing and copy throughput.

You could ship an embedded Postgres fork or require operators to bring their own instance. That buys a familiar query language at the cost of operational surface area this engine is trying not to own. The durable queue here is an implementation detail of migration, not a shared data platform.

Why not just use an embedded SQL database?

SQLite and DuckDB are the natural next guesses once you reject a server. We went down that road: SQL schemas, bulk appenders, status tables, and keyset pulls expressed as queries. SQL is great for ad-hoc review predicates and for getting a prototype honest about joins and filters. It is a weaker fit when the hot path is "append thousands of discoveries, then seek the next thousand pending frontier keys" under a single writer that must not become the scheduler.

Two failure modes showed up repeatedly. First, treating pending work as SELECT … WHERE status = pending (with or without fancy aggregates) makes the database the live lease oracle; under fast flushes that shape got brittle and expensive at tens of millions of rows. Second, the temptation to let the planner join whole node and status relations on every refill looks clean in a notebook and becomes a throughput cliff when each pull only needed a bounded window. The control loop that survived (seal buffer, keyset frontier, memory-first round completion) did not need a SQL runtime underneath it. Badger's sorted keys and batched transactions match that loop more directly.

Why an LSM instead of a B+tree?

An earlier version of this engine ran on BoltDB (a B+tree with copy-on-write pages) and tried to buy read speed with hand-built secondary indexes: membership buckets per status per level, a reverse status-lookup bucket, and bidirectional src-to-dst / dst-to-src join buckets. Each status transition touched several buckets atomically. Reads of known shapes were fast. Write scale was not.

As a B+tree grows, write amplification climbs: each insert or update touches more pages for splits and rebalancing, and Bolt's COW path rewrites those pages on the way down. Past roughly 200K entries on the central nodes bucket, inserts and updates crossed into multi-second territory. Partitioning bought a temporary reprieve and roughly 10× more developer complexity, then the same wall per partition. A larger stress test (~40M source nodes, ~20M destination) grew the file to roughly 100GB: empty membership values meant per-entry overhead dominated the payload, multi-bucket writes stacked amplification on COW, and with no background compaction that bloat stayed until a manual rewrite.

Badger is still a key/value store with secondary indexes; we did not abandon that idea. The difference is the write path: an LSM with a value log absorbs the seal-buffer bulk-append pattern, and compaction reclaims space in the background. Indexes are written on catalog insert and selected by a small planner; they have to earn their keep, but the engine no longer pays B+tree COW amplification on every hot status transition.

Make the database the live task scheduler?

The classic shape (insert a row, SELECT pending work, UPDATE status when done) failed at volume when that table was also the lease oracle. Prototyping hit throughput walls around hundreds of thousands of rows on Bolt, SQLite, and DuckDB when updates dominated and every refill asked the store what was still pending.

The current design still mutates status, but as a sealed overlay beside a sorted frontier, flushed in trusted batches, with the lease queue owning the active round. The rejected shape is not "ever overwrite a status key." It is "make the database the live scheduler on every pull."

Keep the frontier in memory?

This is the obvious first choice, and it looks like it works until you implement it. A prototype held the current source level and its children in RAM until the destination consumed them. If the source ran ahead, the cache grew faster than the destination could drain it. Gating the source per level capped growth but still required roughly two frontier levels in memory at once.

The deeper problem is that RAM does not buy you out of durability. Resumability still requires periodic flushes into the store, so the write cost is only deferred, not removed. Producers (workers finishing tasks) can outrun the consumer (flushing the seal buffer to disk), which is a leaky-bucket problem: you keep going through a DB stall, then pay the same write throughput later with a larger backlog and less safety if the process dies mid-buffer. Under the 20M-row embedded constraint, the current design does not accept that trade. Badger holds the durable frontier; the lease queue is only the live scheduler for the active round.
