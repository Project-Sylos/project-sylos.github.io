A Durable Local Task Engine for Dynamically Expanding Workloads

Design notes from the Sylos migration engine · June 2026

Note on authorship. The prose on this page was produced with AI assistance for raw text generation, but then heavily reviewed, edited, and guided by the author for accuracy and quality.

Abstract. This document presents the design and evaluation of a local-first task engine for very large, dynamically expanding workloads. The motivating use case is filesystem migration, although the techniques generalize to any system in which tasks generate additional tasks during execution.

The paper discusses tradeoffs encountered while implementing durable queue semantics on a single machine, including database selection, append-only event modeling, keyset pagination, checkpointing, and deterministic benchmarking. Performance observations are presented using both real storage devices and a deterministic synthetic filesystem simulator.

The central challenge is not only executing work quickly, but also managing the growth, persistence, and replay of work that recursively generates additional work.

1. Problem statement

Many systems reduce to the same computational shape: a task runs, discovers child tasks, and schedules them. Scientific pipelines, ETL jobs, crawlers, dependency resolvers, build graphs, and migration tools all share this structure. The system forms a dynamically expanding work graph: tasks produce additional tasks until no further work remains. 

Task
 ├─> New Task A
 ├─> New Task B
 └─> New Task C

Anyone building a task queue at scale hits the same imbalance between work generation and work consumption. If tasks are produced faster than workers can process them, pending items accumulate in memory. The backlog grows, RAM grows, and eventually the process dies. That is the failure mode that kills most hand-rolled in-memory designs once traversal starts generating children faster than workers can list directories or call remote APIs.

The opposite case is less dangerous. If workers outpace incoming work, you get idle threads and wasted CPU cycles. That is survivable. Biasing toward starvation over unbounded buffering is usually the safer default.

Sylos amplifies the generation side. Listing one folder can emit hundreds of child tasks in a single batch. During a large run, completed work produces additional work items faster than workers can lease and execute them, round after round. An in-memory frontier does not scale; it is the growing cache described above.

The response was to stop treating the hot queue as the system of record. Workers still lease and process from an in-memory buffer for speed, but discovered nodes and status events are persisted through a DB buffer into DuckDB's Appender as soon as practical. Pending work is pulled back from the database in batches rather than held indefinitely in RAM. That shifts unbounded growth from process memory to disk, which is slower but bounded and resumable. Later sections cover the schema and pull model.

Sylos applies this pattern to one-way migration between two node trees (source and destination). Filesystem traversal is the motivating example; the engine problem is durable scheduling of recursively generated work on a single machine.

2. Non-goals

The engine intentionally does not attempt to provide:

  • distributed execution
  • exactly-once semantics
  • arbitrary dependency scheduling
  • real-time stream processing

The design targets durable, resumable, single-node processing of dynamically expanding work graphs. Dual-tree coordination (Section 7) is an application-layer concern for migration, not a requirement of the core engine.

3. Engine overview

Traversal uses breadth-first search (BFS), not depth-first. BFS requires materializing each frontier level, but it provides predictable round boundaries and a practical way to coordinate two trees in lockstep.

The overall graph is recursive: every task can produce more tasks. What is not recursive is what a single worker does in one shot. Each task handles exactly one node, lists its immediate children, and stops. Children become separate tasks scheduled for a later round. No worker walks an entire subtree in one call; depth is flattened into the queue instead of carried on the call stack.

That distinction matters for filesystem trees in particular. Sibling branches are wildly uneven: one directory might contain millions of descendants while its neighbor is empty. If a worker recursed in-process down a deep branch, it would hold that work for itself while other workers sit idle. You would lose most of the benefit of a concurrent task queue. One-touch-per-task keeps load spread across workers and lets slow branches coexist with fast ones without pinning a single goroutine for hours.

Per task, the steps are:

  1. List immediate children of the current node only.
  2. Apply filter rules; record failures without scheduling further traversal.
  3. Persist passing children and their initial status events; enqueue them as new tasks for the next round.

Workers pull pending tasks in batches, execute traversal, emit status events, and discover child nodes that become new work. Results pass through an in-memory buffer, into DuckDB's Appender API, and flush at round boundaries. Append-only status events are the source of truth for resume, not in-memory queue state alone.

The engine runs in two passes: discovery (traverse and diff both trees) and execution (copy or create after user review). This document focuses on the discovery/traversal substrate.

4. Persistence and scheduling constraints

A tempting pattern: 

INSERT task
SELECT pending task
UPDATE task SET processing

B-tree storage handles transactional workloads well. It degrades under millions of small updates, queue-like access patterns, and append-heavy streams on ever-growing tables. Observed limits during prototyping included:

  • Bolt: acceptable initially; sharp slowdown past ~200K entries in a single bucket (B+ tree growth).
  • SQLite: write throughput degraded past ~400K rows in a single table.
  • DuckDB (row updates): throughput walls and read-after-write inconsistency on the same connection, consistent with cache invalidation rather than immediate visibility of one's own writes.

The structural tension: the engine must write traversal results and read pending work from the same store to schedule the next batch. Pure in-memory processing avoids DB cost but loses resume. Pure synchronous DB round-trips per node do not scale. The resolution was a hybrid scheduling layer (Section 6) plus a different data model (Section 5).

An in-memory node cache was also prototyped: hold the current source level and its children until the destination consumes and compares against them. If the source runs ahead of the destination, that cache grows faster than the destination can drain it. Gating the source until the destination finishes the same level limits the damage but still requires roughly two frontier levels in RAM at once, which does not scale cleanly to very large breadth.

You can partially mitigate by flushing destination results through the DB buffer and evicting source nodes the destination has finished, but that mostly shifts growth into the buffer until the next flush. With enough tuning, a cache-heavy design can trade memory for speed. The current engine does not rely on it; persistence through the database is the default because it bounds memory without sacrificing resume, and the throughput cost is acceptable for the guarantees being purchased.

5. Append-only event model

The fix was stopping in-place mutation of node state.

Instead of: 

UPDATE nodes SET status = 'complete' WHERE id = 123

The schema separates stable node metadata from append-only status history:

  • src_nodes / dst_nodes: path, depth, type, size, etc.
  • src_status_events / dst_status_events: pending on discovery, traversed or failed on completion.

Discovery appends a node row and a pending event. Completion appends a new event row. No updates. No deletes during traversal. DuckDB performs well on this workload because columnar engines favor append-heavy writes and large analytical scans.

Current status is reconstructed by resolving the latest event per node. That cost is paid at diff/review time, not during hot-path traversal. Pseudocode for the idea: 

SELECT latest(status_event)
FROM status_events
GROUP BY node_id

If the database struggles with a workload, the first question is whether the data model forces the wrong access pattern, not whether the database is inherently unsuitable.

6. Architecture: persistence vs scheduling

The runtime separates durable storage from in-memory scheduling: 

                 +----------------+
                 |   DuckDB Log   |
                 | Nodes + Events |
                 +--------+-------+
                          ^
                          |
                   Flush / Appender
                          ^
                          |
                 +--------+-------+
                 |   DB Buffer    |
                 +--------+-------+
                          ^
                          |
                 +--------+-------+
                 |    Workers     |
                 +--------+-------+
                          ^
                          |
                 +--------+-------+
                 | In-Memory Lease|
                 |     Queue      |
                 +--------+-------+
                          ^
                          |
                 +--------+-------+
                 | Pending Tasks  |
                 | (Keyset Pulls) |
                 +----------------+

DuckDB provides durability, checkpointing, and replay after restart. In-memory structures provide leasing, batching, and scheduling latency.

Workers emit status events and child nodes into a DB buffer. The buffer bulk-loads into the Appender; once drained, the Appender is flushed to force a disk write. The Appender maintains its own internal buffer, so the explicit flush is partially redundant. I kept it to define predictable persistence boundaries during development and debugging.

7. Semantics: at-most-once work and dual-tree coordination

Work-generating systems require explicit semantics:

  • no duplicate traversal of the same node
  • no overlapping leases on the same unit of work
  • deterministic progression through the graph
  • resume from durable state after crash or pause

On resume, queues restore round cursors and pull pending work from DuckDB again. The in-memory lease queue is ephemeral; append-only node and event rows in the database are not.

Dual-tree migration adds a coordinator because destination work depends on what the source has already discovered at corresponding levels. The destination needs something to compare against; starting too early would mean missing or incomplete expectations.

The source queue is the independent variable: it can traverse as far ahead as workers and backends allow. The destination queue runs as fast as it can, but only up to source round minus one. For example, if the source is on round 5, the destination must wait on round 4 until the coordinator allows it to proceed. Once the source starts round 6, the destination gets the green light for that round.

Finer-grained gating is possible (localizing coordination to subtrees or partial frontiers), but I chose round-level gating for cleaner separation between the two traversals. The tradeoff is slightly more conservative pacing on the destination side in exchange for simpler invariants and easier reasoning about resume.

Note. The destination queue and round coordinator exist solely because migration requires comparison between two independent trees. For workloads that only traverse or process a single graph, the destination queue can be eliminated entirely. The remaining architecture is considerably simpler:

Generate work → Persist events → Lease batches → Process → Generate more work.

Append-only persistence, resumability, keyset pagination, and lease semantics remain unchanged.

8. Keyset pagination

Pulling pending tasks with LIMIT/OFFSET degrades linearly: offset 50,000,000 implies scanning past 50M rows on every page. I use keyset pagination on monotonic IDs instead: track the starting ID of the next batch (last batched ID + 1), not a cumulative offset. 

-- Degrades at scale
LIMIT 1000 OFFSET 50000000

-- Constant-time seek per batch (given index on id)
WHERE id >= last_id
LIMIT 1000

Level advancement uses soft batch boundaries: if a pull requests x tasks but returns fewer than x, or no row exists at position x+1, the current BFS level is likely exhausted. After the in-memory queue drains, the engine advances to the next level.

9. Benchmarking methodology

Benchmarking traversal engines is easy to do badly. Copying a local Documents folder and reporting elapsed time does not isolate engine behavior from disk variance, OS cache effects, or tree shape. Tests use Spectra, a synthetic filesystem simulator that generates reproducible trees from a seed without real I/O. A separate design note on Spectra covers its modes, architecture, and limitations; this section only describes how it is used for engine evaluation.

Spectra supports arbitrarily large seeded trees, configurable fanout (including heavy-tailed "monster directory" shapes), multi-world projections, and ephemeral mode for no-database traversal benchmarks. Failure injection and latency simulation are configuration concerns; the migration engine's traversal suites exercise recovery, resumption, and throughput under controlled trees rather than live disks.

9.1 Results summary

Environment Observation Interpretation
Real storage (live OS drive) Near parity with Rclone Both systems become I/O bound. Disk, network, metadata latency, and API rate limits dominate.
Spectra ephemeral (synthetic, no I/O) Sylos ~10 to 30% slower than Rclone I/O removed; engine overhead visible (DB persistence, event append, coordination, serialization).

The observed overhead is attributable to persistence and coordination machinery that does not exist in simpler traversal implementations. Sylos pays for a persistent event log, resumable queue state, review-phase metadata, checkpointing, and analytical reconstruction. Rclone's traversal path does not carry equivalent guarantees. Throughput numbers are only meaningful alongside what guarantees they cost.

Under real storage, parity is roughly what physics predicts: once I/O is the bottleneck, architectural differences matter less. Under Spectra, the remaining gap reflects the persistence and coordination machinery described in Sections 5 through 8. It is not an indictment of the approach, but a measured overhead that should be disclosed when evaluating the design.

10. Applicability beyond file migration

The control loop generalizes: 

Generate work → Append events → Lease batches → Process → Generate more work → Repeat

File migration is one instance. The same structure applies wherever local processing must walk a large graph that grows during execution, provided you need durability and can accept append-only reconstruction of current state.
